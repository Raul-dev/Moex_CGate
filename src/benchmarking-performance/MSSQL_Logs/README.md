## **Сравнение стратегий логирования в MS SQL Server 2022 (Проект HttpMustDie)**

В данном документе представлено детальное описание **10 различных инженерных подходов** к организации логирования при высокой параллельной нагрузке 

## ---

**Сравнение механизмов логирования в MS SQL Server (Многопоточность vs Однопоток)**

Данный документ содержит глубокий архитектурный анализ результатов тестирования производительности различных механизмов логирования в **MS SQL Server** с использованием **BenchmarkDotNet**.

В ходе исследования сравнивались два сценария нагрузки, выполняющие **одинаковое суммарное количество операций (2000 вставок логов)** за один замер:

> 1. **Сценарий А (Многопоточный залп):** 20 параллельных потоков приложений делают по 100 записей каждый.
> 2. **Сценарий Б (Однопоточный конвейер):** 1 последовательный поток приложения делает 2000 записей подряд.

**🔍 Архитектурный разбор результатов по методам**

## **1\. SQLCLR \+ RabbitMQ (LogRabbitMQPost)**

Самая парадоксальная аномалия теста: **RabbitMQ работает быстрее в один поток (814 мс), чем под многопоточной нагрузкой (939 мс).**

> * **Что происходило в 20 потоках:** Оптимизированный .NET-код пула каналов (ConcurrentStack\<IModel\>) и сокеты (SocketNodelay \= true) отрабатывали моментально. Однако планировщик SQL Server (**SOS\_Scheduler**) захлебывался. Чтобы выполнить триггер, СУБД была вынуждена 2000 раз параллельно замораживать T-SQL потоки, маршалировать параметры в управляемую память .NET, переключать контекст процессора в среду выполнения SQLCLR и обратно. Возникали жесткие внутренние ожидания контекста.
> * **Что произошло в 1 поток:** Конкуренция за планировщик СУБД исчезла. Переключения контекста выполнялись строго последовательно. Несмотря на то, что сеть дергалась в один поток, отсутствие взаимных блокировок и очередей внутри SQLCLR позволило выиграть **\~125 миллисекунд**.

## **2\. Service Broker (LogServiceBrokerTable)**

> * **В 20 потоках (46.42 ms):** Абсолютный победитель. Команда SEND внутри Service Broker является чисто асинхронной. Она мгновенно перекладывает сообщение во внутреннюю очередь в оперативной памяти SQL Server и отпускает поток приложения. СУБД идеально параллелит эту задачу на все 16 логических ядер процессора i9-9900K.
> * **В 1 поток (221.5 ms):** Скорость упала почти в 5 раз. Поскольку поток всего один, процессор не может задействовать параллельную фоновую обработку очереди. Каждое сообщение встает в стек последовательно, увеличивая общее время ожидания бенчмарка.

## **3\. In-Memory OLTP (LogInMemoryTableTable)**

> * **В 20 потоках (105.10 ms):** Таблицы, оптимизированные для памяти (Memory-Optimized), используют транзакции с оптимистичным контролем версий (Lock-Free). Потоки вообще не блокируют друг друга на логическом уровне, обеспечивая высокую пропускную способность под параллельным прессом.
> * **В 1 поток (688.0 ms):** Самое сильное падение производительности. Движок In-Memory спроектирован исключительно для утилизации сотен параллельных ядер. В один поток накладные расходы на поддержание структуры транзакций в RAM без возможности распараллеливания делают этот метод неэффективным.

## **4\. Дисковые таблицы (LogLocalTable / LogSequentialDiskTable)**

> * **В 20 потоках (\~81-97 ms):** Потоки конкурируют за физические страницы данных на диске и за запись в журнал транзакций (.ldf). Возникает Lock Contention. Оптимизация SEQUENTIAL\_KEY у дисковой таблицы немного спасает ситуацию, снижая задержки на индексах страниц.
> * **В 1 поток (\~484-493 ms):** Время увеличилось кратно. Причина — **Auto-commit транзакции**. Без явного батчинга SQL Server вынужден физически сбрасывать буфер журнала транзакций на диск (вызывать операцию fsync или её аналог) на каждую из 2000 операций последовательно. Время замера начинает напрямую упираться в пиковую скорость задержки (Latency) дисковой подсистемы.

## ---

**💡 Главные выводы исследования (Архитектурные паттерны)**

> 1. **Многопоточность в СУБД — это палка о двух концах.** Механизмы, работающие внутри ядра SQL Server (Service Broker, In-Memory), масштабируются при росте потоков великолепно. Механизмы, требующие выхода за пределы ядра (SQLCLR, вызовы внешних API), при росте потоков деградируют из\-за затрат на планировщик задач СУБД.
> 2. **Прямая синхронная отправка из СУБД в очередь — антипаттерн для Highload.** Даже при идеальном C\#-коде (без локов на соединениях), накладные расходы на маршалинг данных между SQL Server и .NET CLR при 2000 параллельных вызовах создают непреодолимый барьер производительности.

## **🛠️ Как правильно спроектировать слой логирования на основе этих данных?**

Для достижения производительности, превосходящей Service Broker (целевой показатель \< 10 ms в многопоточном режиме), необходимо внедрить паттерн **Transactional Outbox (Асинхронный чейзер)**:

\[Приложение (20 потоков)\]
       │ (Сверхбыстрая запись)
       ▼
\[SQL Server: In-Memory / Local Table\]
       │ (Данные лежат в буфере БД)
       ▼ \[Периодический опрос батчами раз в 5мс\]
\[.NET Worker Service (Внешнее приложение)\]
       │ (Выгребает пачкой по 500 штук за 1 запрос)
       ▼ \[Асинхронный Pure Direct Push\]
\[RabbitMQ / Apache Kafka\]

**Результат внедрения Outbox:** Потоки вашего приложения будут тратить всего **81 мс** (или меньше при батчинге) на сброс логов в базу данных, а тяжелая сетевая работа с RabbitMQ полностью уйдет из контекста транзакций SQL Server, сохраняя ресурсы СУБД для бизнес-логики.

**📑 Описание методов логирования**

## **1\. LocalTable (Тип 1\)**

Классическая прямая вставка (INSERT INTO) в стандартную дисковую таблицу.

> * 
> * **Принцип работы:** Данные пишутся напрямую в таблицу. Каждый поток блокирует страницу данных при обновлении B-Tree дерева.
> * **Узкое место:** Жесткая конкуренция за последнюю страницу данных (**Last-Page Insert Contention / PAGELATCH\_EX**) и задержки журнала транзакций (WRITELOG).
> * 

## **2\. LinkedServerTable (Тип 2\)**

Прямая вставка в таблицу, расположенную на другом сервере, через механизм Linked Server.

> * 
> * **Принцип работы:** Вызывается удаленная процедура или выполняется прямой INSERT через сетевой алиас.
> * **Узкое место:** Огромный сетевой оверхед и использование протокола двухфазной фиксации транзакций (2PC / MSDTC), блокирующий вызывающие потоки.
> * 

## **3\. RabbitMQPost (Тип 3\)**

Отправка лога во внешнюю очередь сообщений (RabbitMQ) напрямую из базы данных.

> * 
> * **Принцип работы:** Внутри процедуры вызывается высокопроизводительная SQL CLR-сборка, которая выступает продюсером и отправляет AMQP-пакет по сети.
> * **Узкое место:** Сетевой стек и затраты ресурсов процессора на маршалинг данных внутри CLR-домена SQL Server.
> * 

## **4\. InMemoryTable (Тип 4\)**

Запись логов в специализированную таблицу в оперативной памяти (In-Memory OLTP).

> * 
> * **Принцип работы:** Используются оптимизированные под RAM таблицы. Движок хранения полностью спроектирован по принципу **Lock-Free** (без блокировок и защелок страниц).
> * **Узкое место:** Ограничено только скоростью работы шины оперативной памяти и процессора.
> * 

## **5\. SequentialDiskTable (Тип 5\)**

Вставка в стандартную дисковую таблицу, оптимизированную под параллельные монотонные ключи.

> * 
> * **Принцип работы:** Кластеризованный индекс создается с включенной системной опцией OPTIMIZE\_FOR\_SEQUENTIAL\_KEY \= ON (доступно в SQL Server 2022).
> * **Узкое место:** Сглаживает конкуренцию в памяти, но физическая скорость диска (I/O) при записи в .ldf журнал остается лимитирующим фактором.
> * 

## **6\. ServiceBroker (Тип 6\)**

Использование внутренней встроенной асинхронной очереди MS SQL Server.

> * 
> * **Принцип работы:** Процедура делает мгновенный SEND сообщения в локальную очередь (Fire-and-Forget). Специальная фоновая активационная процедура вычитывает сообщения и сбрасывает их на диск **пачками (батчами)**.
> * **Узкое место:** Затраты на сериализацию/десериализацию XML или JSON внутри очереди.
> * 

## **7\. SESSION\_CONTEXT (Вариант 7\)**

Сохранение лога в оперативной памяти текущей сессии (SPID) подключения.

> * 
> * **Принцип работы:** Используется встроенный хэш-словарь сессии через sp\_set\_session\_context.
> * **Узкое место:** Данные хранятся только в рамках текущего соединения и недоступны для чтения из других потоков.
> * 

## **8\. TempTable (Вариант 8\)**

Нерегистрируемый или минимально регистрируемый лог через временные таблицы в tempdb.

> * 
> * **Принцип работы:** Вставка происходит в локальные или глобальные временные буферы, где транзакции практически не нагружают основной .ldf файл журнала.
> * **Узкое место:** Общая пропускная способность базы данных tempdb при экстремальной нагрузке.
> * 

## **9\. Extended Events / XEvents (Вариант 9\)**

Генерация кастомных расширенных событий ядра СУБД.

> * 
> * **Принцип работы:** Вызывается системная трассировка через sp\_trace\_generateevent. Ядро SQL Server асинхронно перехватывает событие и пишет в кольцевой буфер памяти.
> * **Узкое место:** Неудобство извлечения данных штатными средствами T-SQL.
> * 

## **10\. RAISERROR WITH NOWAIT (Вариант 10\)**

Прямой асинхронный стриминг текста лога обратно в сеть C\# сервису.

> * 
> * **Принцип работы:** Вызывается информационное сообщение (Severity \< 10\) с инструкцией немедленной отправки в сетевой буфер WITH NOWAIT. Нагрузка на хранилище БД полностью отсутствует.
> * **Узкое место:** Скорость обработки входящего сетевого потока TDS-протокола на стороне C\# клиента.
> *
